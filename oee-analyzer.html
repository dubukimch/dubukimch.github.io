01

FOUR-SYSTEM INTEGRATION

계측 경로와 생산 맥락을 한 설비 키로 결합

Integration Overview는 PLC → Gateway → OEEAnalyzer의 계측 경로와 TwinForge → OEEAnalyzer → TwinForge의 맥락·결과 경로를 분리해 보여줍니다. 두 경로는 불변 equipmentKey로 만납니다.

UI CONTROL

운영자가 조회하는 항목

Equipment Key, UTC From·To와 Refresh Analysis를 사용합니다. 네 Route 카드는 선택 기간의 최신 window에서 생산량, coverage, context ID, 상태와 revision을 가져옵니다.

Equipment keyUTC FromUTC ToRefresh AnalysisRevision
USER FLOW

사용 순서

  1. demo/automotive/main-conveyor와 조회 기간을 입력합니다.
  2. Refresh Analysis로 현재 계산 revision을 요청합니다.
  3. PLC 생산량, Gateway coverage와 TwinForge context ID를 Route 카드에서 확인합니다.
  4. OEEAnalyzer 카드와 Ledger에서 상태·revision·진단 사유를 확인합니다.
WHAT HAPPENS

네 제품이 역할을 나누는 방식

PLC + Gateway생산·불량 누적계수, 상태와 counter epoch를 OPC UA 값·품질·시각으로 제공합니다.
OEEAnalyzer1초 목표 주기로 읽어 oee.integration.v1 Kafka 이벤트와 기간 결과를 저장합니다.
TwinForge작업·제품·계획 구간·ideal cycle을 보내고 같은 설비·기간의 최신 revision 결과를 조회합니다.
  • 계측값과 MES 맥락의 출처와 버전을 각각 추적할 수 있습니다.
  • OEEAnalyzer는 분석 참여자이며 기존 TwinForge → Gateway → PLC 제어 경로를 변경하지 않습니다.
SCOPE · PORTFOLIO VALUE

같은 생산 신호를 여러 서비스가 각자 수집하지 않고 Gateway OPC UA를 계측 경로로 고정했습니다. TwinForge는 작업 맥락을 제공하고 결과를 소비하며, External과 Demo 결과는 Source Mode로 분리합니다.

02

PERIOD ANALYTICS

A/P/Q/OEE와 계산 신뢰도를 함께 조회

Live OEE는 선택한 설비와 UTC 기간의 가용성, 성능, 품질, OEE를 보여줍니다. 숫자만 표시하지 않고 coverage, 결과 상태, reasons와 revision을 함께 제공합니다.

UI CONTROL

조회 조건과 결과 필드

Equipment Key, From, To와 Refresh를 사용해 기간을 조회합니다. 다섯 지표 카드는 status, A/P/Q/OEE와 coverage를 보여주고, Ledger는 생산·불량 증가분, revision, 계산 시각과 diagnostics를 행별로 표시합니다.

EquipmentUTC windowRefreshCoverageRevision
USER FLOW

사용 순서

  1. 분석할 설비와 작업 기간을 선택합니다.
  2. A/P/Q 카드와 생산·불량 증가분을 비교합니다.
  3. coverage가 100% 미만이면 reasons에서 결측 원인을 확인합니다.
  4. Provisional 결과는 지연 허용 시간이 지난 뒤 더 높은 revision의 Final 결과로 확인합니다.
WHAT HAPPENS

기간 결과가 계산되는 방식

AvailabilityRunSeconds ÷ PlannedProductionSeconds로 계획 생산시간 중 실제 가동 비율을 구합니다.
Performance + QualityΔTotal × IdealCycle ÷ RunSeconds와 (ΔTotal-ΔReject) ÷ ΔTotal을 계산합니다.
OEE + confidenceA × P × Q와 유효 관측시간 비율을 반환하고, 결측이면 OEE를 정상 숫자로 꾸미지 않습니다.
  • 분모가 0이면 0%로 단정하지 않고 NotApplicable 사유를 반환합니다.
  • 비율 위반은 100%로 잘라 숨기지 않고 Invalid와 원인을 표시합니다.
SCOPE · PORTFOLIO VALUE

교대·작업·제품 경계와 누적 카운터 증가분을 기준으로 기간 OEE를 계산합니다. 여러 설비 OEE의 단순 평균을 라인 OEE로 표현하지 않으며, 집계 정책이 없는 값은 별도 지표로 유지합니다.

03

TWINFORGE RESULT PANEL

MES 작업 맥락을 보내고 External OEE를 다시 표시

TwinForge의 External OEEAnalyzer 패널은 활성 작업지시를 계산 맥락으로 동기화하고, 같은 설비·기간에서 계산된 A/P/Q/OEE와 coverage를 기존 MES 화면 안에 표시합니다.

UI CONTROL

운영자가 보는 결과와 맥락

External 상태, A/P/Q/OEE, coverage, Equipment, Work order, Product, Context ID와 Last sync를 확인합니다. Sync now는 백그라운드 동기화를 즉시 다시 실행합니다.

Sync nowExternal statusWork orderContext IDCoverage
USER FLOW

사용 순서

  1. TwinForge에서 Automotive MES를 시작합니다.
  2. 활성 작업지시가 선택되고 자동 동기화될 때까지 상태를 확인합니다.
  3. 필요하면 Sync now를 눌러 맥락 전송과 결과 조회를 즉시 실행합니다.
  4. coverage와 calculation status, 최대 세 개의 reasons로 결과 사용 가능 여부를 판단합니다.
WHAT HAPPENS

작업지시에서 분석 결과까지

Boundary lookupMES 시작 이후 Gateway에서 수집된 표본의 source timestamp를 찾아 계산 시작 경계로 맞춥니다.
PUT contexttwinforge-{orderId}와 Idempotency-Key: contextId:version으로 작업·제품·종료·ideal cycle을 전송합니다.
GET result같은 equipment key와 UTC 구간의 최신 window를 조회해 TwinForge snapshot과 패널에 반영합니다.
  • 백그라운드 서비스는 Docker 데모에서 3초마다 동기화하고, 브라우저는 상태를 5초마다 갱신합니다.
  • 맥락은 UTC·최대 31일·양수 cycle·비중첩 계획정지 규칙을 통과해야 저장됩니다.
SCOPE · PORTFOLIO VALUE

TwinForge의 현재 자체 MES OEE는 Demo 출처로 구분합니다. External 분석 모드에서는 Analyzer 결과와 평균하거나 합산하지 않고, 설비·기간·revision이 일치하는 결과만 표시합니다.

04

DATA SOURCES

OPC UA endpoint와 업무 태그를 화면에서 등록

Configuration Workspace는 OPC UA 장치 이름, 보안 정책, endpoint와 node-to-tag 매핑을 관리합니다. 연결 시험과 저장 결과, 현재 등록된 프로토콜 태그를 같은 화면에서 확인할 수 있습니다.

UI CONTROL

운영자가 입력하는 항목

OPC UA 탭에서 Device Name, Security Policy와 Endpoint URL을 입력합니다. 각 node row에는 Node ID, Data Type과 Custom Tag를 지정하고 Add Node·Remove로 행을 관리합니다.

OPC UA tabEndpoint URLSecurity policyAdd NodeCustom Tag
USER FLOW

연결 시험과 저장

  1. Gateway endpoint와 보안 정책을 입력합니다.
  2. 수집할 Node ID마다 데이터 형식과 업무 태그 이름을 지정합니다.
  3. Test Connection으로 현재 endpoint 접속 결과를 확인합니다.
  4. Save Configuration 후 Mapped Tags 테이블에서 저장된 태그와 프로토콜을 확인합니다.
WHAT HAPPENS

설정이 수집 태그가 되는 과정

POST test/api/protocols/opcua/test가 endpoint 연결을 시도하고 성공 여부를 배너로 돌려줍니다.
POST config장치와 OPC UA 구성, node 매핑을 저장하고 protocol tag 목록을 다시 불러옵니다.
Polling일반 OPC UA Worker가 저장된 활성 설정을 읽어 node 값을 protocol data pipeline에 발행합니다.
  • MQTT·Modbus·Kafka/Redis 탭은 같은 workspace에서 환경별 경로를 구분합니다.
  • 이 화면의 일반 데이터 소스 설정과 Docker의 External 4신호 binding은 서로 다른 설정 경로입니다.
IMPLEMENTED BOUNDARY

Data Sources는 범용 프로토콜 태그를 등록하는 운영 UI입니다. 4-System OEE 데모의 Total·Reject·State·Epoch, Source Mode와 stale·skew 정책은 재현 가능한 Docker 환경 변수로 고정하고 Integration 화면에서 실행 결과를 검증합니다.

05

PROCESSING RULES

화면의 처리 규칙과 외부 수집 binding을 구분

Processing Rules의 OEE Logic Builder는 등록된 프로토콜 태그를 설비의 생산량·불량·상태와 ideal cycle에 매핑합니다. 4-System 데모가 사용하는 Gateway endpoint, counter epoch와 품질 정책은 Docker의 Integration binding으로 별도 관리합니다.

UI CONTROL

OEE Logic Builder 입력값

Equipment ID를 입력하고, 등록된 태그에서 totalTag·defectTag·statusTag를 선택한 뒤 Ideal Cycle Time을 지정합니다. 모든 값이 유효하면 Save OEE Mapping이 활성화됩니다.

Equipment IDTotal tagDefect tagStatus tagIdeal cycleSave
USER FLOW

처리 규칙 저장

  1. Data Sources에서 OPC UA 등 프로토콜 태그를 먼저 등록합니다.
  2. Processing의 OEE Logic Builder에서 설비와 세 업무 태그를 선택합니다.
  3. 양수 Ideal Cycle Time을 입력하고 Save OEE Mapping을 누릅니다.
  4. 성공·실패 배너로 저장 결과를 확인합니다. MCC 임계값 규칙은 옆 패널에서 별도로 관리합니다.
WHAT HAPPENS

설정에서 분석 이벤트까지

OPC UA batch readhttp://examples.org/UA/DataAccess/ namespace를 연결마다 해석하고 네 노드를 함께 읽습니다.
Envelope + KafkaUInt64 카운터를 문자열로 보존하고 eventId, 품질, 원본 경로, 시각, epoch와 version을 Kafka에 발행합니다.
Store + query중복 eventId를 제거해 sample·context·revision을 저장하고 설비·UTC 기간별 OEE window API로 제공합니다.
  • Modbus 40020·40022·40025는 Int32 2-register, 40024는 Int16 상태 태그입니다.
  • 기존 속도 40001과 온도 40003을 생산 카운터로 재사용하지 않습니다.
SCOPE · PORTFOLIO VALUE

이 화면의 3태그 OEE 규칙과 External 4신호 분석 계약을 같은 기능으로 과장하지 않습니다. 통합 binding은 Total 40020, Reject 40022, State 40024, Epoch 40025를 1초 주기로 batch read하고, stale 3초·skew 1초·late 5초 정책을 적용합니다.
